# Rejected-Work Memory

Preserve durable reasoning for rejected enhancements so future requests can be matched by concept and need not reopen the same decision blindly.

One record should cover one rejected concept and may link multiple prior requests. Explain the stable product, architectural, or strategic reason. Temporary capacity limits are deferrals, not durable rejections.

During triage:

1. Search existing rejection records by concept, not keyword alone.
2. Present a possible match to the maintainer.
3. On confirmation, link the new request to the existing record and close it through `git`.
4. On reconsideration, revise or remove the stale record and continue normal triage.

Do not create a rejection record for a bug, for behavior that already exists, or for work merely postponed.
